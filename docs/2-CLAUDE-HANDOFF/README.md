- **Server** (`SaveShare.java` only): `GET /session` adds `sha256=` (of the newest `.sav`, lower-case hex, after `size=`). Every file of `/session/save/` carries `X-Content-SHA256` (the whole file's, also on a part) and `Accept-Ranges: bytes`; one `Range: bytes=FIRST-[LAST]` or `bytes=-SUFFIX` is answered `206` with `Content-Range`, a range starting past the end `416`, several ranges or other units the whole file. The checksum and the bytes come from one read of the file.
- **Launcher** (`Copy-W3LanSessionSave` in `W3Lan.psm1`, same parameters plus `-Attempts 3` and `-RetryDelaySeconds 2`): each file goes to `<file>.download` in the co-op `gamesaves`; up to 3 tries (2 s, then 4 s apart), each re-reading the listing; a dropped or stalled connection (30 s without data) resumes with `Range` where it broke off; the file must match the listed size and SHA-256 (the thumbnail its header's), or it is deleted and downloaded again from the start. A save this PC already has (same size and SHA-256) is not downloaded again. If the host saves again between tries, the files start over with the new save. Files of 1 MB or more show a progress bar (MB done, total, MB/s); each retry prints a warning. Verified files then replace the old ones in one step (`File.Replace`, thumbnail first). After the last try: an `IOException` "The host's save did not arrive after 3 tries: <reason>. ... Nothing was written to your co-op saves.", which `Play-LAN.ps1` shows as before, and no `.download` file is left. A 403/404 is not retried and is thrown as its `WebException` (the join password's 403 check in `feature/join-password` reads its status code). The requests skip any system proxy. An older host without `sha256=` is still accepted (size and header checks only).
- **Tests:** `SaveShareTest` 34 (was 11: checksum in listing and headers, resume, closed / suffix / over-long / unsatisfiable / ignored ranges, the range parser). Full `Test-Seamless.ps1` (portable JDK 21) PASS: campaign 255, fact removal 54, save share 34, lobby 14, UDP 465. `Test-SaveDownload.ps1` (new, Windows PowerShell 5.1, a scripted host on loopback, no Java) 18/18: a drop at 600 000 bytes resumes with `Range: bytes=600000-`; a host ignoring Range; damaged bytes refused and downloaded again; damaged or dropped 3 times fails with the message, the earlier save untouched and nothing left; the host saving again mid-download; no thumbnail; a 403 not retried; an unreachable host. `Test-SessionSave` 8/8 (real server, with `-JarPath`), `Test-Lan` 15/15 (with the built JAR copied into `server\` for the run and removed afterwards).
- **Limits:** not tried in the game or across two PCs, and not over a real slow or lossy link. The progress bar is not looked at by any test. The game's own download from the co-op lobby (`FetchSaveFile` in `NativeBridge.cpp`, when the host's newer save is fetched from the main menu) still checks neither size nor checksum and does not resume. Resuming is within one launcher run: a `.download` left by a closed launcher is deleted, not resumed.

**26 October 2026 — Claude Code: connection status in the host console.** Branch `feature/host-status`. For internet play (ZeroTier/Tailscale) the host can now see each player's connection.

- **Server** (`ConnectionStats.java`, new; hooks in `WitcherServer.java`: one line each in the receive loop, `handleMessage`, `broadcastChunk`, `sendText`, the cleanup loop, plus the `status` command and its help line). Counters per UDP endpoint: time since the last packet, packets/s in and out (last 10 complete seconds), longest silence in the last 60 s, and loss from the player to the host, estimated from the movement sequence number the native client already puts on MOVE (field 0) and UPDATE1A/UPDATE1B (field 1; one counter for all three, 1A and 1B share a number). Duplicates and late packets are not loss; a jump over 5000 is a new stream (client restart or wrap). **Ping is `n/a`**: clients echo nothing the server sends, and the campaign request/reply timing includes the client's poll interval. Loss in the host-to-player direction cannot be measured either (no acknowledgements). A one-line summary prints every `statusSummarySeconds` (new key in `server.properties`, default 60, 0 = off) while players are connected. At most 256 endpoints are tracked; idle ones without a player are dropped after 10 s.
- **Launcher:** the host server's console input is a pipe (`Start-W3LanServer` redirects it to send `stop`), so typed commands never reached it. `Play-LAN.ps1` now waits for the game with `Wait-W3LanGame` (`W3Lan.psm1`), which passes typed lines to the server; `stop` is refused there (closing the game stops the server).
- **Tests:** `ConnectionStatsTest` (new, in `Test-Seamless.ps1`): fake-clock checks plus a real server subprocess where one simulated player drops every 10th MOVE (status showed 9.8 % loss) and one sends paired UPDATE1A/1B (0.0 %).
